Card formats

Every card the app draws, drawn — not described. The board specimens are the real renderer's own output; the chat specimens are the app's own React components, server-rendered from the files it ships.

Why this page exists: the shapes were written down in five places, and each copy was one edit away from disagreeing with the others. This is the one page that says what a card IS — and it is generated from the app, so it cannot quietly drift from it.

The one contract

contract

The card kinds, the verify card's fields and a board section's keys live in one file.

The daemon, the MCP tools and the screens all read src/cardContract.js instead of keeping their own copy. A second copy now fails a test the day it is typed, not the day it diverges — the failure this ends was silent, and a silent disagreement about a shape is how a card arrives empty with both ends believing it worked.

refusal

A card the renderer cannot read is refused by name, never dropped.

A section whose text arrives under the wrong key used to be filtered out in silence, so a report could reach the reader as a title above a footer with nothing between. The renderer now names the offending key and the keys it accepts.

Two routes, and the difference is worth knowing. A BOARD card becomes an HTML string in the daemon and is shown inside a sandboxed frame, which is why its look survives into the chat bubble, the board and this page. A CHAT card is never HTML: bounded data goes to the browser and React draws it live, which is what lets its buttons do something.

brief

Seat brief — the ten fields every dispatched seat gets

Filled and pasted as the seat's own prompt, for every seat in every lane, including a solo MAIN-lane executor. It is the brief half of orchestrate step 2 (the dispatch card above is the user-facing half) — both are required. Shown here as its field shape, not the full 31.6KB baseline file.

  1. 1. Impact — ⇄ touches — the map-impact line: what this seat’s write-set touches downstream, and the verifier that proves it.
  2. 2. Role · tier · fresh — the seat’s job, its model/effort tier, and whether it is a fresh seat or a resumed one.
  3. 3. State warning — anything about the target that is not under normal git safety — gitignored paths, a running daemon, another live seat.
  4. 4. Scoped inputs — the write-set (what it may change) plus a read map (what to read first, and nothing else).
  5. 5. Work order — ≤4 items, each with its own acceptance criterion — a longer order returns nothing until the last item lands.
  6. 6. Constraints · blast radius — what the seat must not do, plus the worst case if it goes wrong, how that is contained, and how to restore.
  7. 7. Verifiers — loop-cheap checks run after every item; end-expensive ones run once, at the end, with runtimes named.
  8. 8. Heartbeat — a pre-filled curl the seat runs after every item, so silence and a hung seat never look the same.
  9. 9. Frozen return schema — the exact JSON shape the seat must return — never prose.
  10. 10. If stuck — one line in openQuestions and return what exists, rather than guessing past a blocker.

Source: .claude/templates/seat-brief.md — field shape only, the file itself is not embedded.

Shapes that look alike but are not

Three question cards, and all three stay.

The chat one sends a string, the terminal one sends a keystroke, the planning one posts an answer id. Same look, three different back ends — and each file says so.

A board's "kind" is not a card's "kind".

One tags an archive entry — storyboard, mockup, diagram. The other names a chat block — question, status, report. Same word, different jobs, deliberately not merged.

The rule this page exists to hold

One shape, one definition, everything else reads from it.

A card drawn by hand is a card that will drift, and the drift is silent — which is how a report card reached the user as a title above a footer with nothing in between.

Generated from the app's own renderers — the board specimens are what the daemon emits, the chat specimens are its React components server-rendered. Regenerate rather than edit by hand.
