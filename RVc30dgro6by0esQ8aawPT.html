Card formats — the drawn catalogue

What it is
  • Every card shape the app draws, drawn rather than described — one page, one specimen each, with a line saying where you meet it.
What is in it
  • Board card and scope card, both the real renderer's own output pasted in.
  • Chat cards: question, status, report.
  • Cards that carry an action: verify, activity, plan summary.
  • A short section on the three shapes that look like duplicates but each answer a different back end.
Where it lives
  • Reader → Reference shelf → Card formats. It sits beside your Decisions page and opens the same way.
Open it in the Reader tab. Nothing in it is invented — the board specimens are generated by the app itself.

Why this page exists: decisions were living in chat, in task records and on a review page, and none of those is somewhere you can look things up later. This is the one place that outlives the conversation.

Settled decisions

gates

Ship gates stay per task. Batching them across a session is not taken.

About ten minutes saved against a task of well over an hour, paid for with a hunt across four tasks when something breaks. The numbers came from familiar code and would not survive unfamiliar code.

reporting

The mechanical parts of a report are generated. The judgement parts are written by hand.

Gate results and timings are measurements the machine already holds, and transcribing them loses evidence. Deviations and open worries are where the run gets re-examined, so those stay conscious work.

testing

When a test has to reach around the thing it means to prove, that detour is itself a finding.

Several defects escaped because tests supplied the very thing they were meant to check. The detour is recorded rather than quietly worked around, and a suite that keeps needing them means the seam is wrong.

build

The build stamper keeps importing its hashing helpers from the daemon, awkward layering and all.

One implementation beats two. Drift between the stamper and the checker would be a correctness bug, while the layering is only ugly, and there is no clean alternative because the check runs before the built output can be trusted.

operations

The persistence warning is silenced by a durable marker in the repo, never by an environment setting.

An escape hatch living in the same place as the thing it excuses is circular: satisfying it means repeating the act the warning says will not survive. The marker must also carry a line saying what was done, so a false one is a statement someone typed.

gates

The repository gate latches its first refusal. A tree that recovers mid-run stays refused.

A gate that can flip back to fine is a sample, not a gate. A run that dirties the tree early and cleans it late would otherwise report itself clean, which is the exact case the gate exists to catch.

Design calls on the screens themselves

theme

The account avatar takes the theme accent, in both places it appears.

It was a hard-coded magenta that no other surface used. The desktop rail and the phone drawer carried byte-identical copies, and changing only one would have left the phone unchanged, which was the surface the screenshot came from.

composer

Under the composer sits one small icon, not a card.

The inline card was tried first and rejected on sight for taking the whole area. An icon opens this page in its own tab when it is wanted and costs nothing when it is not.

composer

The icon opens a real browser tab, and refuses to open a broken one.

Every request needs the companion's credential and a new tab cannot carry it in a header, so the link is resolved first. If the credential will not resolve the icon stays visible but disabled, because a vanishing control cannot be explained and a failing tab is worse than no tab.

Storyboards and mockups

Nothing here in picture form yet. Mockups added from here on are appended to this section with the date and the task they belong to.

Appended to as decisions are made. Served by the companion daemon from its own artifacts store.

Where reply and card shapes live today — #1191

The count
  • Three layers define shapes today: the screens (25 renderers), the daemon (11 definition sites), and the written rules (templates plus skills).
  • Only one of the three already has a real single home — every board card the daemon sends renders through one file.
The four real splits
  • The list of card kinds (question, status, report) is typed out three separate times. One test is all that stops the three copies drifting apart.
  • The verify card's fields are written twice, in two different files.
  • The scope card ignores the shared renderer and hand-builds its own HTML with its own colours — and the planner prompt tells a seat to hand-write that HTML too.
  • The dispatch card exists twice on disk and has already drifted: one copy has extra fields, and the skill points agents at its own copy rather than the canon.
Not actually broken
  • The three question cards (chat, terminal, planning) look like duplicates but each answers a different back end. Each file already says why. Leave them.
  • The two board-in-a-frame builders already share their colour file; the split between them is about height rules, not shape.
  • The brainstorm summary card has no row in the written baseline list at all — a gap, not a duplicate.
Found while scouting, now fixed
  • A board card silently threw away any section it could not read — which is exactly why the first version of this card reached you empty.
  • It now refuses out loud and names the problem, with three tests pinning it.
The proposed one home
  • Every shape gets one definition in code, and the daemon, the tools and the screens all read from that one place instead of keeping their own copy.
  • The written baselines stay as the single canon, and the drifted skill copies are replaced with a pointer to it.
  • The scope card moves onto the shared renderer so no seat hand-writes card HTML again.
Scouted read-only. Your call: the full shared contract, or just de-duplicate the four.
