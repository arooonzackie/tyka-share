The boarding gate, rebuilt

The loop around it

Every finished run is written up and sent to a reviewer with no access to how it was produced — only the diff, the results, and what was claimed. Ten entries so far.

  • A send gate refuses an entry that carries reasoning, a plan, or anything secret, before it leaves the process. It has refused entries of ours.
  • Verdicts come back and change the code. Six decisions are settled, including two where the reviewer was shown to be wrong and said so.
  • The sharpest rule came from there: assert what a person would see, not the mechanism meant to produce it. Both defects that got through had passed tests asserting a mechanism.

What it still cannot do

It cannot catch two of the five.

A filter that strips a value is invisible to a check that reads imports, and so is a page that returns an error only to a reader without a credential. Claiming five would be the same over-statement the harness was built to refuse.

The write-set contract does not survive contact with the work.

Six times in one night a change landed outside the file set that had been declared for it. Every one was disclosed. Six is not a run of accidents — it says the boundaries are being guessed rather than derived, and that is a planning fault rather than a discipline problem.

Something moves work out of progress, and nobody knows what.

Three times a task set to in-progress was found parked minutes later, mid-run. Each interruption was cheap enough to absorb, which is exactly why it survived three occurrences without being investigated. It is now a defect with a trace attached rather than a note.

A snapshot of the machinery, not of the product. Every number here was measured on the runs it describes rather than estimated. Nothing described above has been committed.

The complete walk · 8 September 2026

What actually happens between typing a sentence and having code somebody can prove

The section above lists nine doors and what each refuses. This one walks a real request through all of them, adds the two gates that sit outside the spine entirely, and names the file every claim was read out of — so none of it has to be taken on trust.

The worked example is this page

The sentence “show me how the complete harness works and add it to the tyka artifact” was typed into a chat box. Everything below is what the machinery did with it, in order.

01

The front desk writes it down

The sentence becomes a numbered row before anything reads it. It refuses nothing — that is the point. A door that can reject is a door work can be smuggled past; a door that only records cannot be. The row is the receipt: every later stage points back at it, and a task with no row behind it is refused three stages later.

instant
02

Claiming the row is what mints the task

Claiming carries two decisions: which lane (a question, a task, a bug, a feature) and which depth. Only the claim creates the task — boarding one by hand first makes a duplicate that nothing ever joins up. gateSpineEntry in src/loop/flow-gates.js refuses a run with no claimed row and no locked depth, which is what makes “nothing runs without permission” a property of the system rather than a habit of the agent.

instant
03

Alignment — said back in your words, before any code is thought about

A card that says the ask in plain words: what appears on screen, what happens underneath, before and after, the assumptions, what is deliberately out, and how you will know it worked. It is capped in length on purpose — src/loop/align-gate.js refuses a card that runs long or a section that runs to too many lines, because a summary nobody finishes reading is not a summary. Then the lane parks. It is waiting on you, and it will wait as long as it takes.

yours
04

The goal, and the one thing code can actually judge about it

Five sections, listed in src/loop/goalset-flow.js as GOAL_SECTIONS: the goal, the context that cannot be inferred from the repo, the scope with its excluded edge named, the success criteria, and the verification. Five filled sections could be five vague ones, and code cannot tell a good check from a bad one. So it judges the one thing it can: is at least one success criterion something a machine can run and score. isRunnableCheck looks for a command, a real file path, a call, a comparison, an exit status. It knows the phrases that pretend to be checks — “looks right”, “judged as a user” — and a goal made only of those bounces back with its own complaint attached — and that refusal is delivered, not asked about. Since 8 September this door does not park: a refusal is information the run stops on, never a request for a decision.

instant
05

The checklist, and the floor under it

Every item must carry three things, enforced by gateChecklistItem: where it may write, the command that proves it, and what a pass means. An item missing any one of them is refused by name. If the command names a file that does not exist, that is refused too — but only when the answer is a confident no, because a predicate that cannot decide is missing information, not a failure. Then gateProfileChecklist reads the declared write-sets and works out the depth the work actually needs. Declaring a shallow depth for work that writes application source is refused with the offending item named: that is the hole where the flow used to hand itself its own permission at the least strict setting. At full depth the list must also contain an invariant test and an end-to-end test, or it does not pass.

And since 8 September, every verifier is executed once, here, when the checklist is accepted. A command that cannot start — a missing binary, a bad directory, a script name that does not exist — refuses the list and names it. A command that runs and merely FAILS is accepted, because nothing is built yet and a failing assertion is the expected state. This is what replaced the human approval that used to sit beside this door, and it shipped in the same change rather than after it: removing a control before its replacement exists is a gap, not a simplification.

under 5s, plus whatever the verifiers cost to start
06

Dispatch — and the collision map that has to come first

Work goes to fresh seats. Before any of them start, their file sets are written down and proved disjoint: two seats may never hold the same file, and a shared surface gets exactly one writer while everything else queues behind it. A seat also declares its blast radius — the worst thing it could do — and if that worst case reaches outside its declared files, it does not run in the live tree at all. Both rules are written from incidents, not from theory.

3–12 min
07

Verify — the code runs the command, not the thing that wrote the code

Each item is built, then its own verifier is executed by the runner. Green, or a bounded retry that hands the failure back, or that one item escalates alone while the rest carry on. The whole discipline is one sentence: done is what a command proved. A green suite is also not proof on its own — build, type-check, lint and a bundle search have all passed together on a feature that was completely dead, which is why the tests that count drive the running product rather than calling a function directly.

1–7 min
08

Exit — and it compares against yesterday, not against perfect

gateRepoNoWorse refuses a run that leaves the repository worse than it found it. Not red-free: this repository is red today and a block-on-any-red gate would simply never let anything finish, which teaches people to switch gates off. It refuses newly broken, and it counts — a twenty-fifth failure inside an already-failing step used to look exactly like the twenty-four baselined ones. An absent baseline is treated as missing information and never as “nothing is allowed”, on the same doctrine.

under 1 min
09

Your tick is the only thing that closes it

Finished work goes to check, never to done, and it carries its evidence: the files touched, the commands run, their output. Marking your own work done is the one move the flow does not have. That is also the most expensive step measured anywhere in this system — far more of the clock goes on waiting for a person than on anything the machine does.

yours

Two gates that are not in the spine at all

The nine above run in order. These two run whenever their moment arrives, and both exist because the spine alone could be walked around.

●

The boarding gate, at the moment of the write

A hook sits in front of every file write. Before the bytes land it asks one question, in .claude/hooks/lib/write-kind.mjs: is this product code — inside the working tree and not ignored by the repository. If it is, and no task on the board is tracking the change, the write is refused in those words. Two deliberate choices: an undecidable answer counts as product, so the doubt costs a board row rather than an unrecorded change; and a path that is not product is allowed before the board is even contacted, so ordinary scratch work pays nothing. The known hole is written into the file itself — an ignored file that is nonetheless load-bearing passes unboarded.

instant
●

The review exchange, at the moment of sending

Reviews are done by a reviewer who has never seen the reasoning. It gets the project brief, the diff, the pasted results and the acceptance criteria — never the plan, the transcript, or the author’s account of what they built, because a reviewer who watched the reasoning rationalises instead of scrutinising. That rule is enforced rather than remembered: a send gate reads every outgoing entry and refuses it by name if it carries a secret, a forbidden path, a transcript, a plan, or a verdict the author awarded themselves. The format is fixed too — a missing section, or sections in the wrong order, is refused before anything leaves. The protocol is docs/handoffs/review-exchange-protocol.md, and the gate is the code beside it.

instant

The rules the seats live under

  • Fresh, never resumed. One long-lived seat carried five rounds and two dead ends on a single task; a new seat per round is cheaper than the context the old one accumulates. Replying to a returned seat resumes it — which is how two seats once ended up holding the same four files.
  • Read the shared thing once. When several seats would fetch the same source, the session fetches it, filters it, and hands them the file. One board listing measured three megabytes against the hundred kilobytes actually cited.
  • A seat verifies its own file, never the whole repository. A repo-wide command run while a sibling is mid-edit returns real output about a state that never existed — twenty-nine failures across seven untouched files, in one measured case. The session runs the shared gates once, after the last seat is done.
  • Nothing is committed unless you say so. Every gate above can be green with the entire night’s work still uncommitted, and that is the normal state here.

What the repository gate actually runs

Eleven checks in one chain, and the interesting ones are the two that were added the day code that passed every test turned out to be unreachable.

  • Boundaries and manifests — no module reaches into another; every module folder is declared where the app looks for it.
  • File budget — a ratchet, per file. It is currently red on two files, and the fix is to split them, never to raise the number; raising it is how a budget stops being one.
  • Reachability — walks out from the running entry points and fails when a module or route exists that the product cannot reach. An import from a test file counts for nothing, which is exactly how the dead code stayed green.
  • Build output, id shapes, hygiene, the runner, the styling pipeline, the seat-brief map, the review protocol — each one a rule that was broken once and is now checked instead of remembered.

Publishing this page is its own gate

The page you are reading went out through a publisher that asserts before it writes. Render the document, run five rules over it, and only then choose a name, write the file, commit, push. The order is the safety property: every throwing path leaves nothing behind.

  • A credential-shaped string — unrecoverable once public, so it is checked first.
  • A link to a host nobody outside can reach — dead for the reader, or an invitation to leak a session.
  • A link carrying a query string — blunt on purpose, so that the habit of putting a credential in a URL cannot come back on a public surface.
  • Script, or an inline handler — these are documents; one that needs script to show its content is not one.
  • An empty shell — markup that renders to nothing readable, caught directly rather than discovered by a reader.

Nothing goes public by accident either: a page must be deliberately marked before the publisher will touch it, and pressing the control is that act. A refusal names its rule and leaves the mark in place — you did ask; the content was the problem.

Where a run can stop

  • Parked on you, at the alignment card or the goal card. Nothing times out; the lane holds and can be resumed after a restart, because a card the machine re-renders is not lost work.
  • Refused — by the alignment shape, the goal format, or the depth floor. Each refusal is terminal for that attempt and carries the complaint that caused it.
  • Escalated alone — one checklist item exhausts its retries while the others finish.
  • Held at the exit — every item green, but the repository is newly worse than the baseline.

The honest limits, since a page that only lists strengths is marketing.

A gate can only judge shape. It can tell a runnable check from prose, but not a good check from a weak one. The write-set boundary is declared by the same process that then works inside it, which is why it has been crossed and disclosed repeatedly. And the most expensive step in the whole flow is not any of the machinery — it is the wait for a human, which no amount of gating makes faster.

Reference

Every step, and the shape it speaks in

The two documents above say what the harness does and why. This one is the wire: for each step, the door it goes through, the code that owns it, the exact shape going in and coming out, and the sentence it says when it refuses. Every shape here was read off the running code today, not remembered — the refusal strings are copied verbatim, because a paraphrased refusal is a refusal you cannot grep for.

One thing to hold onto before the list: code owns the gates, the LLM owns the content. Every stage below is the same two-part machine — a model drafts, a pure function judges, and the retry is written by the code from the judge's complaint. No stage lets the thing that wrote the answer decide whether the answer was good.

01

Intake — the front desk

POST /api/intake

Your sentence is written down before anything can act on it. This is the only step that refuses nothing: its whole job is that no work exists which the board never saw.

Out

{ "id": "in-8141", "ask": "<your words, verbatim>",
  "msgRef": 8141, "state": "open", "version": 1 }

version is the optimistic lock. Every later write names the version it read, so two seats cannot both claim the same row and both believe they won.

02

Claim — the door that mints the task

POST /api/intake/claim

The fork. You choose a lane (task · bug · feature · question · direct) and a profile (light · bug · full). The claim is what creates the board task — boarding it by hand first makes a duplicate and the flow reads a gap forever.

In

{ "id": "in-8141", "version": 1,
  "lane": "task", "profile": "full", "note": "optional" }

Out — a work lane

{ "ok": true, "lane": "task", "task": { "id": 1130, ... },
  "laneQueued": true }

Out — a question lane, which mints nothing

{ "ok": true, "lane": "question", "task": null, "laneQueued": false }

Absence is never left to be inferred: a lane that mints no task says task: null and laneQueued: false out loud, so a caller can tell “this lane mints nothing” from “something went wrong.” The clock also starts here — the task is created carrying lanePhases: [{ phase: 'claim', ts }], and every duration you are ever shown is measured from that stamp.

03

Entry gate — no claim, no run

gateSpineEntry() · src/loop/flow-gates.js

The choke point that makes “nothing runs without permission” a property of the system rather than a habit of the agent. It is checked at the door, before any model call, so unauthorised work never costs a token.

In

{ "intakeRef": "in-8141", "profile": "full" }

no claim: missing intakeRef · unknown profile: <x> — the profile must be one of light, bug, full.

04

Align — your ask, said back to you

gateAlign() · src/loop/align-gate.js

Before a line of code is thought about, the harness restates what it thinks you asked for and stops. A feature or full claim waits here; a bug gets the same card and keeps walking, because a bug that is misread costs a fix, and a feature that is misread costs a night.

The card — exactly ten fields, nothing else

{ "lane": "task", "profile": "full",
  "ask":        "one line, and it must be ONE line",
  "onScreen":   "what changes where you can see it",
  "underneath": "what changes where you cannot",
  "beforeAfter": { "before": "...", "after": "..." },
  "assumptions": ["...", "..."],
  "out":   "the nearest thing this does NOT include",
  "check": "how you will know it worked",
  "decisions": [{ "question": "...", "recommended": "...",
                  "alternatives": ["..."] }] }

Caps, enforced not suggested

whole card   1500 characters of rendered text
per section  3 lines  (ask: exactly 1)
arrays       1-3 entries

unknown field “x” — the card has exactly these ten fields: … The complaint names all ten, which is what turns a refusal into an instruction. A field the renderer would never draw used to be charged against the ceiling anyway, so a card whose visible text was 200 characters could be refused for something invisible. Two attempts, then the state becomes align-refused.

05

Goal — five sections, one runnable check

gateGoalFormat() · src/loop/goalset-flow.js

The goal states the outcome, never the implementation. The gate judges only two things, and the second is the one with teeth.

Required

goal · contextYouCantInfer · scope · successCriteria · verification

And at least one criterion a machine can score

{ "successCriteria": [
    { "runnable": "node --test test/worktree.test.js" },
    { "text": "the card reads correctly at 390px" } ] }

If a criterion declares a runnable column at all (runnable, verifier, command, check, cmd) it is judged on that column alone — prose sitting beside an empty one does not rescue it. That is deliberate: blending an eye-check into the runnable column is the agent grading its own homework in the one place the design forbids it.

successCriteria must be a non-empty array · and a goal whose criteria are all vibes — looks right, works well, judged as a user, + live — bounces back carrying the complaint. Three attempts, then goal-refused.

06

Checklist — write-set, verifier, acceptance

POST /api/lane/complete · gateChecklistItem()

The goal is decomposed into items, and every item carries the three things that make “done” provable by something other than the agent's word.

One item

{ "id": "the-round-trip-invariant",
  "writeSet": ["claude-companion/test/worktree.invariant.test.js"],
  "verifier": "cd claude-companion && node --test test/worktree.invariant.test.js",
  "acceptance": "Exit 0. Work done in a worktree ARRIVES on the branch,
                 or the branch is untouched and the reason is named.
                 Never a third outcome.",
  "tags": ["test:invariant"] }

The envelope — and the part that trips everyone

POST /api/lane/complete
{ "taskId": "1130", "kind": "checklist",
  "requestId": "checklist-10",     <- REQUIRED
  "draft": [ ...items... ] }       <- a BARE ARRAY, not {items:[...]}

name the requestId of the brief you are answering (checklist-10) · stale draft for X; outstanding is Y. The id is not guessable — the counter is global and already in the hundreds — so the working move is to post without one and read the id the daemon names in its own refusal, then resend. It exists so a planner's late reply to a superseded brief cannot be accepted onto whatever brief happens to be open now.

item [x] verifier cannot run: … — a verifier that fails is fine (nothing is built yet); one that cannot start is not a verifier at all.

07

Profile floor — the depth you cannot talk your way under

gateProfileChecklist() · src/loop/flow-gates.js

The hole this closes is subtle and was real: the gate enforced whatever profile the claim declared, and nothing checked that the declaration was honest — so the rule “nothing runs without permission” quietly wrote its own permission, at the least strict setting. Now the floor is inferred from the write-sets. Touch application source, and you are doing full-profile work whatever you called it.

What each profile owes

bug   first item must carry tag "repro" — the failing test leads
full  one item tagged "test:invariant" AND one tagged "test:e2e"
light no floor — and no write-set that touches product source

profile “light” is below the inferred minimum “full” — item [x] writes application source (<path>), and the refusal tells you which declaration to make instead. Refused checklists land the task at profile-refused.

08

Create — the two writes that join

laneState: 'created'

The work item is raised and the task points at it; the item points back. The state machine the whole flow walks is a fixed vocabulary, and an unknown value is refused at the write rather than stored and puzzled over later:

Every state a task can be in

queued → aligning → awaiting-align → aligned → goal
      → checklist → awaiting-approval → created

direct            the user took this out of the flow by hand
align-refused     the align gate bounced the card past its retry cap
goal-refused      the format gate bounced the goal
profile-refused   the checklist was below the floor for its claim

lanePhases is append-only. A stage never rewrites an earlier stamp, so the clock cannot be made to look better after the fact.

09

Dispatch — the collision map comes first

.claude/templates/seat-brief.md

Before any seat is spawned, each seat's file set is written down and proven disjoint. A shared surface gets exactly one writer and everything else serialises behind it. If you cannot name each seat's paths, you are not ready to fan out — and the honest default verdict is no spawn at all, because only about 12.6% of this repo's commits touch a single module.

The field that makes a bad brief unwritable

Blast radius: <worst-case irreversible effect>
Contained by: worktree | throwaway clone | read-only | reversible-by-git
Restore from: <snapshot ref>

Disjoint file sets prove nothing about a seat that can write outside its set. One tree-level seat voids the map for every other seat in the wave — that is not hypothetical: an interrupted experiment once reset ~193 uncommitted files and destroyed three innocent seats' work, and every other field on the brief was answerable and answered.

10

Verify — code runs the command, not the thing that wrote it

runVerifierOnce() · src/loop/lanes/task.js

The verifier is executed by the harness, and the distinction it draws is the whole point: a test that fails is information, a command that cannot start is a broken promise.

Cannot-start, by exit code and by message

exit 127 · exit 9009
"Missing script" · "not recognized" · "command not found"
"no such file"   · "cannot find module"

And the one that reads backwards until you see it

if (r.error && (r.error.code === 'ETIMEDOUT' || r.signal))
  return { ran: true };

A timeout means it RAN. This was a real bug caught before it shipped: treating ETIMEDOUT as “cannot run” would have refused every Playwright verifier in the repo, because a browser suite is exactly the thing that outlives a short timeout.

11

Exit — measured against yesterday, not against perfect

gateRepoNoWorse() · src/loop/flow-gates.js

A run may not finish clean on top of new breakage. The bar is deliberately not “everything green” — this repo is red today and would never finish. It is no worse than the recorded baseline.

Two ways to be worse

a step failing that the baseline does not accept
a step failing MORE than the baseline records —
  a higher count, OR a count that disappeared

The vanished count is the subtle half. “Unknown is never worse” is right when neither side knows — but a baseline holding a number is proof that a number was obtainable, so losing it means the runner died before it could print one.

repo gate got WORSE than scripts/init-baseline.json — newly failing: <cmds>. A missing verdict or an unusable baseline is a warning, never a block: a gate that fails everyone's work over an absent file only teaches people to reach for --no-verify.

12

Your tick — the only thing that closes it

Nothing above can move a task to done. The harness can only reach check, carrying its evidence; the last step is yours, and no seat may move a board row on your behalf.

Three gates that are not in the spine at all

The boarding gate — at the moment of the write

.claude/hooks/lib/write-kind.mjs

Not a stage but an interception: it fires on the tool call itself, so an agent that decides to skip the flow is stopped by the same machinery whether it meant to or not. Rules in files are promises; this is code.

Publish — render, then assert, then write

services/publish/src/assert.ts

Five rules, and the ordering is the safety property: everything is checked before anything is written, so a refused page leaves nothing behind to find.

The five, in the order they are checked

credential     an API key or token in the bytes
gated-host     the loopback names, the v6 loopback, the gated app host
query-string   a URL carrying parameters
script-tag     executable markup
empty-content  nothing worth serving

The four gated hosts are described rather than spelled, and that is not squeamishness — the rule matches any occurrence anywhere in the bytes, so a page that names them is a page that cannot be published. This one tripped it on the first attempt and was rewritten rather than smuggled past, which is the only honest way to treat a gate you also happen to own.

PublishRefused[gated-host] — every rule names itself in the message, because “publish refused” with no reason is a stall. PublishRefused is a 400 (the content is wrong, and you must change it); PublishBlocked is a 409 (the flag or the source, not the content). This page went through it.

The snapshot — new today

src/git.js · src/secretScan.js · src/worktree.js

Every 30 minutes the daemon writes the working tree to refs/vfp-snapshots/<branch> — a real commit, in a throwaway index, that never moves HEAD and never runs a hook. Two things changed today, and both because a worktree is now cut from these commits rather than from the branch tip.

It says what it holds

before   snapshot 2026-09-08 13:11:22
after    snapshot · 3 files · claude-companion/src, test, docs/plans

And it is scanned before the ref moves

{ "ok": false, "committed": false, "refused": "secret",
  "error": "snapshot refused: a credential-shaped string would be
            stored (path). Nothing was written to <ref>." }

A real commit passes through gitleaks first, on the argument that a leaked key cannot be un-leaked — deleting the line later fixes nothing, because history keeps it and the actual remedy is cancelling the key. The snapshot was the one path in this repo that wrote a tree with no scan, which was tolerable while it was only a safety net and stopped being tolerable the moment other work started branching from it. It still fails open on a missing scanner, and says the scan was skipped — the same posture the commit hook takes, for the same reason.

And the merge back, which is the actual safety property

{ "ok": false, "refused": "conflict",
  "conflicts": ["a.txt"], "unchanged": true,
  "error": "merge refused: 1 conflicting file — a.txt.
            main is unchanged." }

The parallel bargain is guess disjoint, verify at the merge, fall back to serial — so a merge that cannot fail cleanly is not a verification, it is a coin toss with a tidy log. On conflict the merge is aborted, the paths are named, and the branch is left byte-for-byte where it was. Never a third outcome.
